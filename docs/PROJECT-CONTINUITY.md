## هدف این دفتر

این فایل نقطهٔ شروع هر ادامهٔ کاری در چت‌های آینده است. هدف آن حفظ دانش پروژه در خارج از حافظهٔ یک حساب کاربری یا یک گفت‌وگوی خاص است. هر جلسهٔ مهم باید وضعیت، تصمیم‌ها، خطاها، تغییرات و گام بعدی را در همین ساختار یا فایل‌های پیوست آن ثبت کند.

> اصل تداوم: هیچ تصمیم مهم، راه‌حل، خطای شناخته‌شده یا تغییر رفتاری نباید فقط در چت باقی بماند.

## وضعیت فعلی پروژه

پروژه یک برنامهٔ حسابداری کارگاه به‌صورت local-first و PWA است. داده‌ها در مرورگر نگهداری می‌شوند و قابلیت خروجی/بازیابی JSON و اتصال اختیاری به Google Drive دارد. حوزه‌های فعلی شامل طرف حساب، کالا و واحد، انبار، فاکتور خرید و فروش، عملیات مالی، بانک و صندوق، چک، تخصیص FIFO، تولید، گزارش‌ها، تنظیمات و پشتیبان‌گیری است.

ریپوزیتوری اصلی منبع حقیقت کد است. ریپوزیتوری `rasool083/Accounting-` منبع تاریخی و مستندات اولیهٔ مدل‌های Excel/Sheet و گفت‌وگوهای آغازین محسوب می‌شود. فایل‌های Google Drive و Google Sheets منبع داده‌ها، مثال‌ها و نسخه‌های پشتیبان هستند؛ آن‌ها بدون بررسی تاریخ و نسخه نباید منبع حقیقت کد تلقی شوند.

## ریسک‌های باز و حل‌نشده

این موارد باید در هر برنامه‌ریزی آینده در نظر گرفته شوند:

1. قرارداد قیمت و واحد باید در مدل با `priceBasis` و نمایش صریح واحد قیمت تثبیت شود.
2. هستهٔ تقویم جلالی و اختلاف روز یکسان‌سازی شده است؛ نمایش صریح `dayBasis` و آزمون UI با دادهٔ واقعی هنوز باقی است.
3. موجودی کالا و ماندهٔ حساب‌ها projection مستقیم هستند، نه حاصل دفتر رویداد بازسازی‌پذیر.
4. حذف انبار و کالاهای دارای ارجاع باید به آرشیو یا خطای وابستگی تبدیل شود.
5. کاردکس باید بالانس، مصرف واقعی تولید، nested production و snapshot را کامل نمایش دهد.
6. تست integration/UI با fixture عملیاتی غیرحساس هنوز کافی نیست.
7. پرتال مشتری بدون authentication، tenant و Row-Level Security قابل انتشار نیست.
8. برای APK باید migration، PWA cache، quota، backup/restore و update موبایل جداگانه آزموده شوند.

بنابراین **۴ مرحلهٔ توسعه‌ای و ۱ مرحلهٔ انتشار نهایی** باقی مانده است.


## ۱۴۰۵/۰۶/۳۱ — تکمیل مرحلهٔ reversal فاکتور خرید

مرحلهٔ آزادسازی پرداخت در ویرایش، ابطال و حذف فاکتور خرید با commit بعدی این جلسه تکمیل می‌شود. پرداخت‌های اختصاصی آزاد می‌شوند، اما پرداخت‌های FIFO مشترک میان چند فاکتور حفظ می‌گردند. چک مشتری، چک شریک و رویداد نقدی/بانکی هرکدام مسیر reversal مستقل دارند و از ایجاد reversal تکراری جلوگیری می‌شود.

آزمون‌های مرحله ۲۹ مورد موفق بودند و type-check و build نیز موفق شدند. هشدار build دربارهٔ بزرگ‌بودن chunk جاوااسکریپت مانع انتشار نیست و به مرحلهٔ بهینه‌سازی عملکرد منتقل می‌شود.

**گام بعدی:** مرحلهٔ کنترل حساب‌ها و مغایرت بانکی شامل projection-first، انتقال بین حساب‌ها، گزارش مغایرت و کنترل رویدادهای سررسیدشده.


## ۱۴۰۵/۰۶/۳۱ — تکمیل مرحلهٔ کنترل حساب‌ها و مغایرت بانکی

گزارش تطبیق حساب‌ها اکنون برای بانک، صندوق و شریک، ماندهٔ ثبت‌شده را با ماندهٔ بازسازی‌شده از دفتر نقدی مقایسه می‌کند و اختلاف، دریافت، پرداخت و تعداد رویدادها را نمایش می‌دهد. انتقال بین حساب‌ها و ماندهٔ افتتاحیه با آزمون مستقل پوشش داده شدند.

در ممیزی اجرایی، خطای preview ناشی از دو مسیر React کشف شد. تنظیمات Vite مخزن و محیط preview با alias و `dedupe` برای React و ReactDOM اصلاح شدند. بعد از اصلاح، dashboard، صفحهٔ بانک‌ها و صندوق‌ها و گزارش‌ها در مرورگر قابل اجرا و قابل مشاهده بودند.

اعتبارسنجی نهایی این مرحله ۳۱ تست موفق، type-check، build و diff check است. هشدار حجم chunk تولیدی همچنان غیرمسدودکننده است و به بهینه‌سازی عملکرد منتقل شد.

**گام بعدی:** سخت‌سازی PWA و آماده‌سازی APK، شامل migration، backup/restore، service worker، offline و آزمون موبایل.


## ۱۴۰۵/۰۶/۳۱ — آماده‌سازی زیرساخت APK و تفکیک اپ مشتری

زیرساخت Capacitor برای APK مالک کارگاه آماده شد. `capacitor.config.ts` با شناسهٔ مستقل `ir.workshop.accounting`، مسیر build وب و سیاست عدم mixed content اضافه شد. وابستگی‌های Capacitor و فرمان‌های `android:init`، `android:sync` و `android:open` به package اضافه شدند.

محیط فعلی Java دارد، اما Android SDK و `adb` ندارد؛ بنابراین ایجاد پوشهٔ native Android و build نهایی APK به محیط دارای Android Studio/SDK منتقل شد. این موضوع مانع build وب و PWA نیست.

ممیزی معماری اپ مشتری تکمیل شد. اپ مشتری باید برنامه‌ای جدا با applicationId جدا، backend احراز هویت‌شده و Row-Level Security باشد. استفاده از APK مالک، localStorage، لینک دارای partyId یا فایل JSON کامل کارگاه برای مشتری مجاز نیست. قرارداد کامل در `docs/APK-AND-CUSTOMER-APP-ARCHITECTURE.md` ثبت شد.

**گام بعدی:** نصب Android SDK در محیط build، اجرای `android:init` و ساخت APK debug؛ هم‌زمان طراحی schema و policyهای backend مشتری با یک tenant آزمایشی.


## ۱۴۰۵/۰۶/۳۱ — تصمیم توقف انتشار APK تا پایان آزمون واقعی

کاربر تصمیم گرفت پیش از ساخت و انتشار APK release، چند دوره با نسخهٔ فعلی وب/PWA کار کند و اشکالات، ابهام‌ها و اصلاحات قابل مشاهده را ثبت و اعمال کند. بنابراین پوشهٔ Android و زیرساخت Capacitor حفظ می‌شوند، اما انتشار APK به مرحلهٔ بعد از آزمون پذیرش واقعی منتقل شد.

APK مالک کارگاه در همین مخزن نگهداری خواهد شد تا موتور حسابداری، تست‌ها، migration و پوستهٔ Android یک منبع نسخه‌گذاری داشته باشند. اپ مشتری در آینده مخزن جدا و معماری مستقل خواهد داشت؛ زیرا فقط‌نمایش مشتری باید با Auth، API و RLS امن اجرا شود و نباید bundle یا localStorage برنامهٔ مالک را به ارث ببرد.

سیاست update شامل versionCode افزایشی، signing key ثابت، backup قبل از migration، بازسازی ledger پس از migration و انتشار رسمی از کانال امضاشده است. remote code loading برای نسخهٔ حسابداری فعال نمی‌شود.

**گام جاری:** دورهٔ استفادهٔ واقعی با نسخهٔ وب/PWA، ثبت ایرادها بر اساس تاریخ شمسی و مرجع فاکتور/چک، سپس اصلاح و آزمون مجدد پیش از هر APK release.


## ۱۴۰۵/۰۶/۳۱ — ممیزی عمیق پارامترها، تراکنش‌ها و چاپ A4

ممیزی عمیق ارتباط مدل‌ها و صفحات انجام شد. مسیرهای تولید، بسته‌های تو‌در‌تو، مصرف و بهای بچ، تبدیل واحد پایه، قیمت فروش، FIFO فاکتورها و چک‌ها، پرداخت خرید، تعهد شریک، دفتر موجودی، دفتر نقدی، انتقال حساب، گزارش تطبیق و backup بررسی شدند. نتیجهٔ اجرایی این بود که چاپ عمومی صفحه قابل اتکا نیست؛ بنابراین پنج مسیر چاپ اصلی به scope مستقل A4 منتقل شدند.

یک خطای حسابداری در رویداد پرداخت خرید اصلاح شد: پرداخت نقدی/بانکی خروج وجه است و باید در دفتر نقدی منفی باشد. schema اکنون ۵ است و migration داده‌های قدیمی مثبت را اصلاح می‌کند. این migration فقط جهت رویداد ناسازگار را اصلاح می‌کند و برای رویدادهای مثبت دریافت یا opening دست‌کاری انجام نمی‌دهد.

برچسب‌های گزارش‌ها نیز اصلاح شدند تا قیمت پایهٔ فروش با بهای تمام‌شده یا سود ناخالص قطعی اشتباه نشود. بهای واقعی تولید همچنان از snapshot و `unitCost` بچ‌ها می‌آید و قیمت فروش از تاریخچهٔ قیمت/ورودی دستی مستقل است.

اعتبارسنجی پس از اصلاح: ۳۲ تست موفق، type-check موفق، build تولیدی موفق و diff check موفق. هشدار bundle بزرگ باقی است و در مرحلهٔ بهینه‌سازی performance پیگیری می‌شود.

**گام بعدی پیشنهادی:** دورهٔ استفادهٔ واقعی با ثبت سناریوهای روزانه، سپس افزودن fixture یکپارچهٔ end-to-end برای خرید، پرداخت چندردیفی، خرج‌کردن چک مشتری، چک شریک، reversal، فروش و بازسازی ledger؛ پس از آن تصمیم نهایی دربارهٔ انتشار APK گرفته شود.


## ۱۴۰۵/۰۶/۳۱ — تکمیل آزمون یکپارچهٔ خرید، چک و reversal

fixture یکپارچهٔ عملیات در تست هسته اضافه و تأیید شد. سناریو دو فاکتور خرید تأمین‌کننده را با سه پرداخت پوشش می‌دهد: چک مشتری، پرداخت نقدی و چک شریک. تخصیص FIFO، رویداد خروج نقدی، رسیدن چک شریک به تاریخ جلالی سررسید، حذف فاکتور اول، بازگشت چک مشتری به وضعیت «نزد ما»، reversal پرداخت نقدی و ابطال/reversal تعهد شریک بررسی شدند.

وضعیت اعتبارسنجی فعلی: **۳۳ تست موفق، type-check موفق، build تولیدی موفق و diff check موفق**. هشدار bundle بزرگ همچنان صرفاً بهینه‌سازی performance است و مانع ادامهٔ کار نیست.

**گام بعدی:** اجرای همین سناریوها در محیط preview با دادهٔ نمونهٔ قابل پاک‌سازی، سپس طراحی دفتر ثبت خطاهای دورهٔ استفادهٔ واقعی و تکمیل fixtureهای فروش/تولید برای پیش از APK.


## ۱۴۰۵/۰۶/۳۱ — رفع باگ ثبت فاکتور با تخفیف کامل

در مسیر submit فاکتور، شرط وابسته به `calculatedAmount` باعث می‌شد فاکتوری که کل مبلغ آن تخفیف خورده و مبلغ نهایی‌اش صفر است اصلاً ذخیره نشود. شرط به subtotal مثبت منتقل شد و محاسبهٔ مبلغ خالص در helper مستقل قرار گرفت. اکنون تخفیف کامل، تخفیف بیشتر از subtotal و تخفیف منفی رفتار کنترل‌شده و تست‌شده دارند.

اعتبارسنجی پس از اصلاح: **۳۵ تست موفق، type-check موفق، build تولیدی موفق و diff check موفق**. هشدار bundle بزرگ همچنان غیرمسدودکننده است.


## ۱۴۰۵/۰۶/۳۱ — اصلاح فهرست Google Drive و طراحی بکاپ پایدار APK

علت نمایش‌ندادن بکاپ‌های کوتاه‌شده پیدا شد: query Drive فقط `accounting-workshop-backup` را جست‌وجو می‌کرد. query و فیلتر client به marker `backup` اصلاح شدند؛ بنابراین نام قدیمی `accounting-workshop-backup-initial-...json` و نام جدید `backup-...json` هر دو فهرست می‌شوند.

دو تست Drive اضافه شد و اعتبارسنجی نهایی **۳۷ تست موفق، type-check موفق، build موفق و diff check موفق** بود. برای APK، بکاپ خودکار بدون مجوز مکرر به نشست وب فعلی قابل تضمین نیست؛ مسیر درست در مستند معماری ثبت شد و شامل OAuth native/Keystore یا backend امن، صف pending، ارسال هنگام اتصال شبکه، snapshot نسخه‌دار و backup اجباری پیش از migration است.


## ۱۴۰۵/۰۶/۳۱ — تکمیل Supplier Directory و سابقهٔ استعلام

صفحهٔ مستقل «دفتر تأمین‌کنندگان و استعلام‌ها» به navigation اضافه شد. این صفحه برای تأمین‌کنندگان بالقوه‌ای است که ممکن است هیچ خریدی از آن‌ها انجام نشده باشد. مدل مستقل شامل `Vendor` و `VendorQuote` است و با localStorage جداگانه ذخیره می‌شود.

رابط شامل فرم‌های ثبت/ویرایش تأمین‌کننده و quotation، جست‌وجو، فیلتر ماده و نوع فعالیت، برچسب مواد قابل تأمین، جزئیات تماس، سابقهٔ استعلام و تحلیل کمترین/میانگین/آخرین قیمت و تغییر درصدی است. ساختار از حسابداری جداست و هیچ ledger یا فاکتوری ایجاد نمی‌کند.

تحقیق طراحی و مراجع در `docs/VENDOR-DIRECTORY-DESIGN.md` ثبت شد. اعتبارسنجی: **۳۹ تست موفق، type-check موفق، build موفق و diff check موفق**.

**گام بعدی پیشنهادی:** آزمون دستی صفحه با چند ماده مانند پتاسیم اگزالات و چند تأمین‌کننده، سپس افزودن import/export مستقل دفتر و بعداً ماتریس امتیازدهی وزنی و هزینهٔ تحویل.


## ۱۴۰۵/۰۷/۰۱ — سخت‌سازی Supplier Directory

پس از بررسی مرحلهٔ اول، سخت‌سازی دفتر مستقل اجرا شد. داده‌های دفتر اکنون با format اختصاصی `vendor-directory-backup-v1` export/import می‌شوند؛ import فایل حسابداری یا ساختار ناقص را رد می‌کند و جایگزینی را با تأیید کاربر انجام می‌دهد.

یک اشکال تحلیلی نیز اصلاح شد: quotationهای با واحد یا ارز متفاوت قبلاً ممکن بود در کمترین قیمت و میانگین مخلوط شوند. از این مرحله، شاخص‌های قیمت فقط بر اساس مبنای هم‌واحد و هم‌ارز جدیدترین quotation محاسبه می‌شوند و واحد مبنا نمایش داده می‌شود.

اعتبارسنجی این مرحله باید شامل تست round-trip backup، رد فایل نامعتبر، رد مقایسهٔ ناهم‌واحد، type-check، build و diff check باشد. گام بعدی پیشنهادی پس از آزمون دستی: ماتریس امتیازدهی وزنی کیفیت/قیمت/تحویل/ریسک و سپس export CSV یا گزارش مقایسهٔ چاپی.


اعتبارسنجی نهایی مرحلهٔ سخت‌سازی با **۴۱ تست موفق**، type-check موفق، build تولیدی موفق و diff check موفق انجام شد. دو failure اولیه از فرض نادرست تست دربارهٔ مبنای مقایسه بودند و با تفکیک `quoteCount`/`comparableQuoteCount` و تثبیت قرارداد «جدیدترین quotation به‌عنوان basis» اصلاح شدند.
